# .NET CPU 热路径

## 先看 JIT 生成的代码

- 查看汇编代码时要关注实际调用点：辅助方法内联后，周围代码仍会影响寄存器分配、常量加载和指令顺序
- 数学上等价的 C# 写法，JIT 未必生成相同的机器码，要结合实际调用路径比较机器码和性能
- 源码顺序会影响 JIT 的输出，可以尝试交错编排互不依赖的计算，或提前加载数据，但不要指望用 C# 精确控制指令顺序
- 不要用指令数、栈帧大小或机器码长度直接判断性能优劣；即使没有值因为寄存器不足而被写入栈中，关键依赖链、加载延迟、SIMD 寄存器与通用寄存器之间的数据搬运和缓存压力仍可能主导性能
- x64 和 ARM64 能用同一套写法就不必拆分，只有确认该写法在某一架构下生成的代码明显较差时，再分别处理

## 标量与 SIMD 的数据流

- 展开循环、把状态移到循环外、合并循环都要看总成本，既要算减少循环控制、方法调用和状态写回带来的收益，也要算代码膨胀和寄存器压力带来的代价
- 临时值的生存期应尽量缩短；中间结果该保留、重算还是重新读取，要看哪种方式的总成本最低
- 提前加载只有在能隐藏延迟时才有价值；如果它妨碍 JIT 直接使用内存操作数，或让太多值同时存活，就等到临近使用时再加载
- 先在方法入口统一完成边界检查，再逐步推进 `ref`，减少重复的索引扩展、地址计算和范围检查；数组、`Span` 和 `ref` 要分别确认各自的生成代码
- 只向量化部分计算时，向量结果应尽快使用，减少元素提取和重排，减少 SIMD 寄存器与通用寄存器之间的数据搬运，也避免先把数据写入栈再读回
- 不要想当然地认为向量越宽、并行度越高就越快；转换、尾部处理和寄存器压力都应计入成本，有时使用窄向量，甚至改用标量，反而更快
- JIT 通常会消除 `IsSupported` 分支，但支持某个 ISA 不代表对应路径一定更快；还要看实际工作量，并把分派放在核心循环外
- 如果通用向量 API 能在所有目标 ISA 上生成高效代码，就应优先使用，否则再改用对应的 `intrinsic`

## 内联、泛型和内存布局

- `AggressiveInlining` 不要滥用，先查看内联后的整体生成代码；较大或很少被调用的方法使用 `NoInlining` 有时反而更快
- 当 JIT 能确定泛型实参的实际类型时，值类型的受约束调用和静态抽象成员调用通常能避开装箱和间接调用，但仍需检查生成的代码；实例接口调用还可能多出一次检查
- 在只读上下文中调用结构体的非只读成员时，编译器可能先复制整个结构体；改用可写的 `ref`，或把成员声明为只读，以避免这种防御性复制
- `InlineArray` 适合保存固定大小的状态，但要通过 `ref`、`Span` 或索引原地访问；较大的结构应避免按值传递，也要留意 `readonly` 字段引发的防御性复制
- `Unsafe.SkipInit` 不会去掉方法级的 `.locals init` 标志；只有局部变量清零确实带来明显开销时，才考虑在合适范围内使用 `SkipLocalsInit`，并检查 IL 和 JIT 输出
